## Approach picked: A1 — disable Kotlin-side compaction in `toMeshData()`

The mesh's `extruderIndices` should already be file-filament-indexed at
the native boundary; the Kotlin-side `compactExtruderIndices` call
inside `NativePreviewMesh.toMeshData()` was added under B88 to make the
**old plate-narrowed palette** match a compacted mesh. Phase 2 changed
the palette contract: it is now file-filament-indexed (sourced from
`info.detectedColors`, file-wide). The Kotlin-side compaction is now
the bug — for Buzz Lightyear plate 9 it remaps raw paint-state indices
7 / 9 (file filaments 8 / 10) down to 0 / 1, which the canonical
palette resolves as file filaments 1 / 2 (black + blue) instead of
8 / 10 (peach + white).

A1 was preferred over A2 (parallel "file-indexed" output) and A3
(Kotlin-side inverse remap) because:

- **Smallest diff.** Two-line change in `toMeshData()` — replace
  `compactExtruderIndices(extruderIndices)` with a verbatim copy.
- **No new state to thread.** A2 / A3 would require extra plumbing
  (a second ByteArray field, or a remap table sourced from the
  canonical list at the call site). A1 piggybacks on data the mesh
  already carries.
- **Native already does the right thing.** The native side preserves
  paint-state indices for MMU files (`compactPreviewIndices` skips
  when `has_mmu_data == true`) and runs sorted-unique compaction for
  non-MMU files. For non-MMU files the file uses filaments 1..N
  densely (Calicube, S-Buttons), so the native compaction is the
  identity map — file-filament indices already align with the
  canonical palette. Removing the Kotlin compaction restores the
  identity for the MMU case too.
- **Helper retained.** `compactExtruderIndices` stays as a companion
  helper for any future caller that needs sorted-unique compaction
  (e.g. legacy slot-narrowed paths). The `NativePreviewMeshCompactionTest`
  unit tests on the helper still pass — they exercise the helper
  directly, not via `toMeshData`.

## Files changed

Inside `toMeshData()`:

- Replaced `val compactedIndices = compactExtruderIndices(extruderIndices)`
  with `val previewIndices = extruderIndices.copyOf()`.
- Updated the comment block to record the Phase 2 contract: mesh
  `extruderIndices` are file-filament-indexed, the canonical palette
  is sized to the file's filament count.
- Updated the constructor argument `extruderIndices = compactedIndices`
  → `extruderIndices = previewIndices`.

The companion helper `compactExtruderIndices` is unchanged and
unreferenced from `toMeshData`. It remains exposed for the unit tests
in `NativePreviewMeshCompactionTest` (which still document the
sorted-unique compaction algorithm for any caller that opts into it).

### `app/src/test/java/com/u1/slicer/viewer/NativePreviewMeshTest.kt`

Two existing tests asserted the pre-Phase-2 compaction contract.
Both are updated to assert the Phase 2 file-filament-indexed contract:

- `toMeshData converts triangle payload into mesh data` — input
  `[0, 3]` previously asserted compacted output `[0, 1]`. Now asserts
  preserved output `[0, 3]`.
- `toMeshData compacts sparse extruder indices to match colorMapping
  palette` — renamed to `toMeshData preserves sparse extruder indices
  for canonical palette lookup`. Input `[0, 3, 4, 6, 9]` previously
  asserted `[0, 1, 2, 3, 4]`. Now asserts preserved `[0, 3, 4, 6, 9]`.

Both updates flip the **assertion** to match the Phase 2 contract;
neither weakens an existing invariant. The B88 contract was
"compaction aligns with plate-narrowed palette" — that contract is
gone with Phase 2.

## Risk assessment

- **Native-side compaction interaction.** `compactPreviewIndices` runs
  in C++ for non-MMU paths. With my change, that compaction still
  runs, and for non-MMU files it produces `0..N-1` sorted-unique
  output. For files where filaments 1..N are dense (the common case),
  this is the identity map and the canonical palette resolves
  correctly. **Edge case:** a non-MMU file with sparse filament use
  (e.g. file declares 8 filaments, only filaments 1, 5, 8 appear in
  the mesh) would have native compaction remap to `0, 1, 2`, and the
  canonical palette `palette[0..2]` would resolve filaments 1, 2, 3
  — wrong. This case is **out of scope for A1**; fixing it requires
  C++ changes (disable native compaction or pass through the
  unique-set as a side channel).

  No fixture in the project exercises this edge case today —
  per-object multi-extruder Bambu files (Calicube, S-Buttons,
  Dragon Scale plate 3, F1 calendar) use filaments 1..N densely.

- **B88 regression risk.** The B88 unit tests on
  `compactExtruderIndices` still pass — they call the helper
  directly. The two `toMeshData`-level tests are updated as described.
  No instrumented test asserts the old compaction contract.

- **H2C benchy decimated test (instrumented).** Not run (per
  constraints) but traced by hand: the test asserts triangles with
  `extruderIndices == 5` get green from a 7-entry palette where
  `palette[5] = green`. My change preserves the raw native value `5`,
  so palette lookup is unchanged. **Expected to pass.**

- **S-Buttons plate 1 Prepare test (instrumented).** Asserts ≥4
  distinct mesh indices and ≥4 distinct RGBA clusters under the
  canonical palette. Native produces dense `0..3` for this case
  (per-object diversity, no paint data, sorted-unique compaction is
  identity). My change preserves `0..3`. **Expected to pass.**

- **Layer-tool path (`recolorByZBands`).** Not affected by this
  change. Z-band recolor reads `extruderBambu` from
  `LayerToolSegment`, not from `mesh.extruderIndices`. Regression #3
  is out of scope here.

- **Performance.** `extruderIndices.copyOf()` is O(triangles), same
  cost as the LUT-based compaction. No regression.

A1 fixes regression #2 only. The other two regressions are
adjacent but require separate changes:

- **Regression #1** (G-code Preview): requires either widening
  `GcodeRenderer.extruderColors` to file-filament size, OR adjusting
  `normalizeGcodePreviewColors` to map T-indices through the
  canonical palette. This is the Phase 2 §4 Step 7 (Preview side)
  follow-up; the current `normalizeGcodePreviewColors` build a
  4-entry slot-indexed array which is the wrong shape after Phase 2.
- **Regression #3** (layer-tool): requires either keeping
  `info.detectedColors` file-wide for layer-tool plates (matching
  the SEMM behaviour at line 3770 of `SlicerViewModel.kt`), OR
  rebuilding `narrowedColors` to always include filament 1 (the base
  colour) so `extruderBambu = 1` resolves to a non-yellow entry.

Both follow-ups are data-side fixes in spirit (matching Approach A's
philosophy) but live in different files than the mesh-recolor path.
They are out of scope for this exploration to keep the diff small
and the risk surface narrow; documenting them here so the reviewer
can integrate fixes b/c if a sibling approach addresses them.

## Native rebuild required?

**No.** The fix is Kotlin-only. The native side already produces
file-filament-indexed values for MMU paths and a sorted-unique
compaction for non-MMU paths. The bug was in the Kotlin layer's
extra compaction.

If a future change wanted to also disable the **native** compaction
(to handle the sparse non-MMU edge case noted under Risk), that
would require touching `sapil_model.cpp:587-589` and a native
rebuild. Not required for A1 as scoped.
