## §0 The bug pattern — one-paragraph reframing

The 3D Prepare preview's recolor path indexes a "palette" by the mesh's
extruder-index space. After Phase 2's canonical-driven palette change,
the palette is **file-filament-indexed** (palette[0] = file's filament 1,
palette[7] = file's filament 8, …). But the mesh's `extruderIndices`
aren't in the same index space across all file shapes:

- **Per-object multi-extruder** (Calicube, S-Buttons plate 1) — mesh
  indices ARE file-filament-indexed → the canonical palette aligns.
- **Multi-plate Bambu after native plate-load with paint data**
  (Buzz plate 9, file uses filaments 8 + 10) — native skips compaction
  (`has_mmu_data == true` preserves state_idx for H2C-style folding)
  and Kotlin's `NativePreviewMesh.compactExtruderIndices` then maps the
  raw indices to 0..N-1 in sorted-unique order. So mesh has indices
  {0, 1} representing filaments {8, 10}. The canonical palette gets
  indexed at slot 0, slot 1 → returns filaments 1, 2 (black, blue) —
  WRONG.
- **Layer-tool / Hueforge** (flippy plate 4) — mesh has no per-vertex
  colour at all; recolor goes via `MeshData.recolorByZBands` indexed by
  `extruderBambu - 1` (1-based file filament index). The
  `info.detectedColors` list is plate-narrowed by `mergeThreeMfInfoForPlate`
  for layer-tool plates (down to 1 entry in the symptomatic case), so
  every Z-band coerces to palette[0] and the body paints solid yellow.

## §1 Approach C summary — synthesise mesh-aligned palettes

Make the canonical filament list match each mesh's index space by
producing a separate **mesh-aligned** palette flow that the recolor
effect prefers when available, while leaving the existing
`resolvedFilamentColors` flow (file-fileIndex aligned, drives the chip
strip and the G-code preview's slot-mapped palette) untouched.

The new flow `SlicerViewModel.meshAlignedFilamentColors`:

```
combine(_threeMfInfo, _filamentOverrides, _layerToolOnly, _canonicalFilamentList) {
  info, overrides, layerToolOnly, canonical ->
    val canonicalEntries = canonical?.filaments ?: return@combine emptyList()
    val withOverrides = canonicalEntries.map { entry ->
        overrides[entry.fileIndex]?.color ?: entry.color
    }
    if (layerToolOnly) return@combine withOverrides   // full canonical, fileIndex-aligned
    val used = info?.usedExtruderIndices?.filter { it > 0 }?.sorted().orEmpty()
    if (used.isEmpty()) return@combine withOverrides
    used.mapNotNull { idx -> withOverrides.getOrNull(idx - 1) }
}
```

**Indexing contract (encoded in the docstring):**

- `layerToolOnly == true` → palette[i] corresponds to file filament
  `(i + 1)` (1-based extruderBambu indexing the recolorByZBands path
  uses).
- `layerToolOnly == false` → palette[i] corresponds to the i-th
  distinct file-filament-index used on the current plate, in
  sorted-ascending order. Matches the
  `NativePreviewMesh.compactExtruderIndices` algorithm exactly.
- Empty when `_canonicalFilamentList` is null (STL / non-canonical
  paths). Recolor effect falls back to `resolvedFilamentColors`, then to
  the slot palette, mirroring the existing fallback chain.

**Caching.** A `_canonicalFilamentList` MutableStateFlow caches the
file's full canonical list once on every `currentModelFile` change
(setter-triggered, IO-dispatched so Buzz-Lightyear-sized paint walks
don't block the load). The flow re-emits when overrides edit, so the
recolor reacts in real time.

The existing `resolvedFilamentColors` flow is unchanged. The recolor
effect in `InlineModelPreview` simply prefers
`meshAlignedFilamentColors` when non-empty:

```kotlin
val canonicalSource = meshAlignedFilamentColors.takeIf { it.isNotEmpty() }
    ?: resolvedFilamentColors
```

### What stays the same

- `resolvedFilamentColors` — drives the chip strip, the G-code preview's
  slot palette, and the SingleColorFilamentRow display. All three of
  these expect file-fileIndex (= `info.detectedColors`) alignment, so
  the StateFlow contract is unchanged.
- `bambuCanonicalList` and `applyOverridesToCanonical` — re-used as-is.
- `compactExtruderIndices` — re-used as-is. The new flow is designed to
  produce a palette that matches its sorted-unique compaction directly.
- `mergeThreeMfInfoForPlate` / `buildThreeMfInfoFromNative` — no changes
  to their `detectedColors` semantics. The mesh-aligned flow reads
  `info.usedExtruderIndices` and reorders the canonical full file list.

## §3 Coverage — does this fix all 3 reported regressions?

### File 7 (Buzz plate 9) — YES

Trace:
- File has 11 declared filaments. Plate 9 uses filaments 8 and 10
  (1-based; raw 0-based 7 and 9).
- Native skips compaction (paint data present).
- `compactExtruderIndices` maps raw {7, 9} → mesh {0, 1} in sorted order.
- `info.usedExtruderIndices = {8, 10}` (1-based) → sorted [8, 10].
- `meshAlignedFilamentColors = [canonical[7].color, canonical[9].color]`
  = [peach, white].
- `MeshData.recolor` uses palette[mesh[i]]: index 0 → peach, index 1 →
  white. CORRECT.

### File 5 (flippy plate 4, layer-tool) — YES

Trace:
- File declares ≥2 filaments (dark, yellow). Layer-tool segments
  reference both with `extruderBambu = 1` and `extruderBambu = 2`.
- `_layerToolOnly = true` → `meshAlignedFilamentColors` returns the full
  canonical list `[dark, yellow]` (NOT plate-narrowed).
- `recolorByZBands` uses palette[extruderBambu - 1]: 1 → dark, 2 →
  yellow. Z-bands now show both colours. CORRECT.

### File 6 (S-Buttons plate 1) — PARTIAL

Trace:
- Prepare screen: `info.usedExtruderIndices = {1, 2, 3, 4}` →
  `meshAlignedFilamentColors = [c0, c1, c2, c3]`. Mesh has compact
  indices 0..3. CORRECT — Prepare 4 distinct colours.

But the user-reported failure for File 6 is on the **G-code Preview**
(post-slice), not the 3D Prepare preview: *"G-code Preview after slice
shows 3 colours (red collapsed to brown)"*. That symptom is a
slot-mapping collision in `colorMapping`, not a mesh-alignment issue.
The G-code preview renders the **slot palette** (4 entries indexed by
physical slot), and `normalizeGcodePreviewColors` collapses to
slot-keyed colours via `colorMapping.indexOfFirst { it == slot }` — when
two file filaments map to the same slot, only the first contributes.

Approach C does NOT change `normalizeGcodePreviewColors` and therefore
does not fix this G-code Preview symptom. The cleaner fix is orthogonal:
either (a) make the G-code preview palette canonical-indexed (would
require the renderer to look up by file-filament-index, not slot), or
(b) drive the G-code preview's slot palette from the file's filaments
even when `colorMapping` collapses (already the existing behaviour for
the first-mapped slot — the issue is the second filament loses
visibility). Both are larger reshapes that belong with the Phase 2.4b
filament-mapping dialog work.

**Coverage summary:** 2/3 user-visible symptoms resolved by this
approach. The third (S-Buttons G-code Preview red collapse) is a
separate bug class that any of A/B/C is unlikely to fix in isolation.

## §4 Risk assessment

### What the approach handles correctly

1. **Buzz-style high-index paint plates.** The sorted-narrowing matches
   `compactExtruderIndices` exactly. Validated by code-walk; no
   instrumented test added (per the constraint).
2. **Per-object multi-extruder (Calicube, S-Buttons Prepare).** Native
   compacts → mesh has 0..N-1 → `usedExtruderIndices = {1..N}` (1-based)
   → palette = canonical[0..N-1]. Identity-preserving.
3. **Layer-tool plates.** Full canonical bypasses `mergeThreeMfInfoForPlate`'s
   narrowing for the recolor path; chip strip / dialog still see the
   narrowed `detectedColors` (correct UX behaviour — the chip strip
   should show only filaments-used-on-this-plate).

### What could break

1. **Async canonical load.** Moving the canonical refresh off the setter
   onto `Dispatchers.IO` introduces a brief window where the recolor
   uses `resolvedFilamentColors` (legacy, file-fileIndex aligned). For
   Buzz plate 9 this means a sub-second flash of "wrong colour" on
   first paint before the canonical flow emits. The race-guard
   (`if (_currentModelFile === file)`) ensures stale loads don't
   overwrite a fresher one. No user-visible regression beyond the brief
   flash; the recolor effect re-fires when the StateFlow updates.

2. **Files where `info.usedExtruderIndices` disagrees with the mesh's
   actual filament indices.** The flow assumes
   `info.usedExtruderIndices` is the authoritative "file-filament
   indices present on this plate". If `buildThreeMfInfoFromNative` /
   `mergeThreeMfInfoForPlate` ever mis-report (e.g. filament 5 listed
   as used but native excluded it from the mesh), the palette would
   diverge from the mesh. The existing tests
   (`BambuPlateStateRegressionTest`, `BambuFixtureHarnessTest`,
   `NativePreparePreviewTest`) cover the major fixtures and would catch
   regressions; the production path has been hardened by B81/B82/B92
   work to keep these aligned.

3. **STL flow.** `_canonicalFilamentList` is null for STL (because
   `canonicalListAtLoad` returns null). Flow is empty; recolor falls
   back to `resolvedFilamentColors` (also empty for STL since
   `info.detectedColors` is empty for non-canonical files), then to the
   slot palette. Same behaviour as before. No risk.

4. **Single-colour 3MFs.** Canonical has 1 entry; mesh has 0..0 indices
   (single value). Palette has 1 entry. Layer-tool branch returns the
   1-entry palette unchanged. Per-vertex branch finds
   `usedExtruderIndices = {1}` → palette = [canonical[0]]. Mesh index 0
   → palette[0]. Correct.

5. **Override-on-Prepare reactivity.** `_filamentOverrides` is in the
   `combine` set; flow re-emits on every override edit. Validated by
   the existing `_filamentOverrides.drop(1).collect { … }` slice-stale
   wiring already in `init {}`.

### What this does NOT address

1. **G-code Preview slot collisions** (S-Buttons "red collapsed to
   brown"). Different code path; needs separate work.
2. **Slice-time embed.** `meshAlignedFilamentColors` is purely a
   recolor-display flow; it does not feed `ProfileEmbedder`. Slicing
   continues to use the canonical full list verbatim, matching the
   Phase 2 §4 Step 6 contract.
3. **The chip strip / SingleColorFilamentRow.** Both keep reading
   `resolvedFilamentColors`, so chip swatches and dialog defaults
   continue to reflect file-fileIndex semantics. Intentional —
   Approach A and B may take a different position on this.

---

## §5 Verdict

Two of the three regressions resolved cleanly by adding one
StateFlow. No native rebuild. No public contract changes.
JVM suite stays green.

The third regression (S-Buttons G-code Preview) is out of scope for any
mesh-aligned palette approach — it's a slot-collision symptom in the
G-code preview's slot-keyed renderer. If the deciding hand picks C,
that one needs a separate change, ideally folded into the Phase 2.4b
filament-mapping dialog work since the user-visible behaviour
("filaments mapped to the same slot share a colour") is the design's
intended overlap behaviour.
