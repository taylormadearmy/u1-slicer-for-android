# B46 Handoff: colored_3DBenchy Prepare Preview Regression

## Status: Not Fixed — Needs Native Path Routing

## What the user wants
The colored_3DBenchy Prepare preview should look clean and smooth with 4 distinct color regions, as it did in **v1.5.0**. Currently there are two issues:
1. **Missing color regions** — color boundaries within the model are not shown (e.g. the hull should have a color change halfway up, the door should have color detail). These are visible in the sliced gcode preview but missing in the Prepare preview.
2. **Triangle seam artifacts** — speckled/noisy appearance at color boundaries from TriangleSelector subdivision creating sub-triangles with mismatched normals.

## When it broke
**Between v1.5.0 and v1.5.1** (commit `1d9d19b` "feat: layer-change pipeline on v1.5.0 baseline (clean port)", release `035e987`).

### v1.5.0 (working)
```kotlin
// MainActivity.kt ~line 1974 — ALL 3MF used native path
modelFilePath.endsWith(".3mf", ignoreCase = true) ->
    com.u1.slicer.NativeLibrary().getPreparePreviewMesh()?.toMeshData()
```

### v1.5.1 (broken)
```kotlin
// Kotlin ThreeMfMeshParser introduced for 3MF with colorMapping/extruderMap
if (colorMapping != null || extruderMap != null) {
    ThreeMfMeshParser.parse(file, extruderMap, colorMapping?.size ?: 0)
} else {
    NativeLibrary().getPreparePreviewMesh()?.toMeshData()
}
```

The Kotlin `ThreeMfMeshParser` path does TriangleSelector expansion (`emitTriangleSelectorTriangles` + `splitTriangle`) which subdivides base triangles at color boundaries. These sub-triangles have flat normals that don't match adjacent base triangles, creating visible **seam artifacts** — the speckled/noisy appearance at color transitions.

The native path uses C++ `get_facets()` which groups triangles by TriangleSelector state (clean per-state mesh groups) and QEM decimation (smooth, connectivity-preserving simplification). No seams.

### Subsequent changes that further complicated routing
- `c0d4700` added `hasPaintData` gate so only painted models go through Kotlin
- `bf56c5d` (B45) added `colorMapping` gate and blocked rotation effect for painted models

## The fix

Route painted 3MF preview back through the native `getPreparePreviewMesh()` path, like v1.5.0 did.

### Why this isn't a one-line revert

1. **Timing**: `getPreparePreviewMesh()` requires the model to be loaded in the C++ engine first. The current code has a race between the main LaunchedEffect (which fetches the mesh) and the ViewModel's model loading pipeline. In v1.5.0 this worked because there was only one path. The current code has two LaunchedEffects (main + rotation) that can race.

2. **H2C index folding**: The native C++ (`sapil_model.cpp:462-464`) maps TriangleSelector `state_idx` directly to `extruder_index = state_idx - 1` without folding dual-AMS states. For H2C models, this produces indices 0-9 instead of 0-3. The `MeshData.recolor()` palette only has 4 entries, so indices 4-9 get clamped to index 3 (wrong color). Fix needed in `NativePreviewMesh.toMeshData()`:
   ```kotlin
   val foldedIndices = extruderIndices.copyOf()
   for (i in foldedIndices.indices) {
       val idx = foldedIndices[i].toInt() and 0xFF
       if (idx >= 4) foldedIndices[i] = (idx % 4).toByte()
   }
   ```

3. **My attempt failed**: I tried calling `getPreparePreviewMesh()` directly in the main LaunchedEffect for `hasPaintData` models. It worked on the Pixel 8a but the user reported an empty plate on their device — likely the native model wasn't loaded yet when the call was made.

### Suggested approach

Study how v1.5.0 handled the timing (tag `v1.5.0`, `MainActivity.kt` around line 1970). In v1.5.0, the LaunchedEffect keyed on `modelFilePath, extruderMap, colorMapping?.size, previewTooLarge` and called `getPreparePreviewMesh()` directly. There was no `hasPaintData` split or rotation effect conflict.

The cleanest fix might be:
- For `hasPaintData` 3MF, call `getPreparePreviewMesh()` in the main LaunchedEffect BUT gate on a signal that the native model is loaded (e.g. a StateFlow from ViewModel that's set after `loadModel()` completes)
- Add the H2C index folding to `NativePreviewMesh.toMeshData()`
- Keep the rotation effect guard to skip painted models (they don't support rotation in preview anyway)

### What NOT to do
- Don't try to fix the Kotlin TS expansion seams — the proper fix is to not use TS expansion at all for preview (use native path instead)
- Don't broaden `resolvePreviewModelFile` to use rawInputFile for all painted models — breaks calicube and other non-H2C models

### C++ changes are OK
Fixing H2C index folding in `sapil_model.cpp:462-464` directly (so the native path outputs correct indices) is a valid alternative to folding in `NativePreviewMesh.toMeshData()`. This would require a native `.so` rebuild.

## What was investigated in this session (no code changes committed)

1. **H2C state folding in `paintIndexForState`** — states 5-8 → 1-4 when `isH2cProject`. Correct but irrelevant for the preview path since the sanitized file only has states 1-4.

2. **`hasPaint` threshold** — TS state >= 2 (was > 3). Correct for H2C merge path but not on critical path.

3. **`ThreeMfInfo.isH2c` field** — detected from `project_settings.config` markers. Note: colored_3DBenchy does NOT trigger this because it has Snapmaker `@U1` profiles, not `@BBL H2C`.

4. **TS expansion disable (majority vote)** — `dominantTriangleSelectorPaintIndex` walks TS tree without subdividing. Produces correct color distribution but loses color boundaries within individual base triangles (hull color change, door detail).

5. **Native path routing** — worked on Pixel 8a, empty plate on user's device. Timing issue.
