## B.2 — Invert config pipeline (move U1 hardware out of `sapil_print.cpp`)

### What the reviewer flagged

> The goal of a "native-first read pipeline" is undermined by the fact that U1 physical hardware limits (Arachne wall generator defaults, max volumetric speeds, deretraction speeds) are hardcoded directly inside `sapil_print.cpp`. The slicing engine is not a modular component receiving a machine profile from Kotlin; it is permanently and rigidly coupled to the U1 hardware via C++ inline strings and floats.

### Current state

`applyConfigToPrusa` in `sapil_print.cpp:169-450ish` writes ~40 hardcoded values into the Slic3r `DynamicPrintConfig`:
- Per-extruder arrays sized to `n_ext`: temperatures, retraction, cooling, volumetric speed.
- Machine kinematic limits (max_speed_x/y/z/e, max_acceleration_*, jerk_*).
- Per-feature accelerations (outer_wall, inner_wall, top_surface, travel, initial_layer).
- Wall generator defaults (Arachne / classic), seam, brim, ironing.
- Plate type, extruder offsets, single_extruder_multi_material defaults.

These values are U1-specific and live in C++. The `is_snapmaker_profile` gate skips some of them when the embed already covers them.

### Proposed shape

Move the U1 hardware profile to a Kotlin-side `U1MachineProfile` data class. Build a fully-resolved `Map<String, Any>` in Kotlin: `BaseU1Profile + 3MF canonical params + user overrides`. Push the resolved map through JNI as the single source of truth. Native side becomes:

```cpp
applyKotlinResolvedConfig(dpc, kotlin_resolved_keys);
```

No more C++ branches for "embed wins / clamp to U1 default". Kotlin owns the merge.

### Migration plan (5 chunks)

1. **Inventory** — extract every `dpc.set_key_value(...)` call from `applyConfigToPrusa` into a structured list. Group by category (kinematics / per-extruder / cooling / feature speeds / etc.). Identify which are gated by `is_snapmaker_profile` and which are unconditional.

2. **Define `U1MachineProfile`** Kotlin data class — one value per native key. Default constructor returns the values currently hardcoded in `applyConfigToPrusa`. Tests: pin every value against the current C++ value (cross-check via differential test).

3. **Add JNI accessor** — `nativeApplyResolvedConfig(json: String)` that takes a fully-resolved JSON map and applies each key to the engine's `DynamicPrintConfig`. Removes the type-juggling in C++ (it just reads from a map of strings).

4. **Migration loop** — for each `applyConfigToPrusa` write, move it to Kotlin's resolved-map builder. Keep the C++ write in place but conditionally skip if the key is in the resolved map. Differential test (`GcodeBaselineDiffTest`) gates each step — every key migrated must produce identical G-code header output.

5. **Cleanup** — once every key is migrated, delete `applyConfigToPrusa` body. The native side becomes a passthrough.

### Risk assessment

- **Print correctness risk**: HIGH. `applyConfigToPrusa` writes directly affect the slicer's internal state. A missed key, wrong type, or wrong gate produces silently-wrong slices.
- **Mitigation**: anchor each chunk to a `GcodeBaselineDiffTest` pass. The harness already captures ~60 watched keys + G-code templates + body head/tail across 5 fixtures. Each chunk passes when the diff vs the prior commit is empty.
- **Test scope**: full instrumented sweep + 22-fixture E2E batch + differential per chunk.

### Estimated scope

Multi-day. Chunk 1 (inventory) is ~1 day. Chunks 2-5 are ~1-2 days each with verification. Total: 5-10 days assuming clean tests at each step.

### Out-of-scope simplifications worth considering

- The keys where the Phase 2 narrowed gate *intentionally* clamps (hot_plate_temp, fan_*, retraction, volumetric, slow_down, flush) — these are hardware-tuned and don't need Kotlin override surface. Keeping them hardcoded in Kotlin's `U1MachineProfile` is fine; the goal is "single source of truth", not "user-overridable".
- Per-feature jerk values stay hardcoded (no UI to override).

## B.3 — Replace `PRINT_START` heuristic with explicit profile metadata

### What the reviewer flagged

> Searching for the substring "PRINT_START" in the machine start G-code is a robust, mathematically sound proxy for "This is a native Snapmaker profile"? Reality: this heuristic is a ticking timebomb. PRINT_START is the ubiquitous standard macro for Klipper firmware. If a user imports a generic 3MF file originally prepared in Bambu Studio for any Klipper-based printer (Voron, RatRig, etc.), the substring match will yield a false positive.

### What's already landed (partial)

- `ProfileEmbedder.kt` writes `snapmaker_authored_profile = "1"` to the embedded `Metadata/project_settings.config`.
- `sapil_print.cpp` has a comment explaining the upgrade path; still uses the PRINT_START heuristic.

### What's left

The native side currently ignores the marker because OrcaSlicer's `PrintConfig.cpp` doesn't register `snapmaker_authored_profile` as a `ConfigOptionString`. `model_config.option<Slic3r::ConfigOptionString>("snapmaker_authored_profile")` returns null for unregistered keys.

Two possible paths:

#### Path A — register the key in OrcaSlicer's schema

Modify `app/src/main/cpp/upstream/OrcaSlicer/src/libslic3r/PrintConfig.cpp` to add:

```cpp
def = this->add("snapmaker_authored_profile", coString);
def->label = L("Snapmaker authored profile marker");
def->tooltip = "Set to '1' by U1 Slicer's ProfileEmbedder. Native uses this to gate is_snapmaker_profile detection without the PRINT_START false-positive.";
def->set_default_value(new ConfigOptionString(""));
```

Then in `sapil_print.cpp`:

```cpp
auto* marker_opt = model_config.option<Slic3r::ConfigOptionString>("snapmaker_authored_profile");
if (marker_opt && marker_opt->value == "1") {
    is_snapmaker_profile = true;
} else {
    // Fallback for non-marker paths.
    auto* start_opt = model_config.option<Slic3r::ConfigOptionString>("machine_start_gcode");
    if (start_opt && start_opt->value.find("PRINT_START") != std::string::npos) {
        is_snapmaker_profile = true;
    }
}
```

Risk: low. Adding a ConfigOptionString to PrintConfig.cpp is a contained schema addition. OrcaSlicer's option lookup is non-destructive for unrecognised values, so existing code paths stay unchanged.

#### Path B — bypass `model_config.option<>()` and read the key directly from JSON

Before the JSON is parsed into `model_config`, scan the raw bytes for `"snapmaker_authored_profile":"1"`. Avoids touching the OrcaSlicer schema. Less clean but no upstream changes.

Either path requires native rebuild + instrumented sweep verification.

### Recommended approach

Path A. The schema addition is small; the result is structurally clean. The native rebuild + sweep follows the standard checklist (CLAUDE.md "Native Rebuild" section).

### Estimated scope

Half a day: schema addition (~10 LOC), native rebuild (~10 min on existing build dir), instrumented sweep (~2h via sharded runner), commit.

## Open questions for the user

- **B.2 priority**: realistic value vs effort? If U1 hardware never changes (single product line), the cost of not doing B.2 is ongoing maintenance friction in C++ — bearable. If a future hardware variant lands (different bed temp range, different kinematics), B.2 becomes load-bearing. Worth scoping with a concrete timeline before committing the multi-day refactor.

- **B.3 priority**: the false-positive risk is real but bounded. ProfileEmbedder rewrites `machine_start_gcode` to U1's PRINT_START template before the native check sees it, so Bambu-Klipper foreign profiles in practice don't reach the gate with their original start G-code. The only realistic path that bypasses ProfileEmbedder is a direct legacy load of pre-marked Snapmaker 3MFs (where the heuristic correctly fires). B.3 is "no tech debt cleanup" rather than "active risk mitigation" — its value is structural correctness, not preventing live regressions.
