# Design: B39 + C1 + F46
**Date:** 2026-03-28
**Scope:** Three independent improvements to U1 Slicer Android

---

## B39 — Eliminate plus-screen flash during file picker load

### Problem
When the user selects a file via the system file picker, the app returns to the foreground showing the `Idle` (plus/home) screen. There is a visible gap before `loadModel()` is called and emits `SlicerState.Loading`, during which the plus screen is shown. On slow devices or cloud-backed file providers (Google Drive), `getFileDisplayName()` can extend this gap further, causing users to think the selection didn't register and tap again.

### Design
**One new ViewModel method + one call site change in `MainActivity`.**

Add `fun setLoadingFromPicker()` to `SlicerViewModel`:
```kotlin
fun setLoadingFromPicker() {
    _state.value = SlicerState.Loading("Loading…")
}
```

In `MainActivity.filePickerLauncher` callback, call this as the **very first line** before any filename resolution:
```kotlin
) { uri ->
    uri?.let {
        viewModel.setLoadingFromPicker()          // ← new: immediate Loading state
        val name = viewModel.getFileDisplayName(it) ?: ""
        if (name.isEmpty() || SlicerViewModel.isSupportedFile(name)) {
            viewModel.loadModel(it)
        } else {
            viewModel.showUnsupportedFileError(name)  // resets state to Idle + error
        }
    }
}
```

If the file is unsupported, `showUnsupportedFileError` already resets state — no extra cleanup needed.

### Files changed
- `app/src/main/java/com/u1/slicer/SlicerViewModel.kt` — add `setLoadingFromPicker()`
- `app/src/main/java/com/u1/slicer/MainActivity.kt` — call it at top of picker callback

### Testing
No new unit test needed (trivial state assignment). Verify manually: pick a large file from Google Drive — plus screen should not appear after picker closes.

## C1 — Remove dead upgrade-guard diagnostics

### Problem
Two fields in `DiagnosticsStore` were added to track post-upgrade slice behaviour that is no longer monitored or acted on. They add noise to the diagnostics output and maintenance surface without any current value. `clipperRetryAttempted` is confirmed active and must not be touched.

### Dead code to remove

**`sessionHasPostUpgradeGuard: Boolean`**
- Private var + public getter
- Written by `markUpgradePendingForCurrentSession()` and `markSliceSucceeded()`
- Read only in `markSliceStart()` (a guard that no longer does anything useful) and diagnostic report output
- Remove: var, getter, all write sites, the guard block in `markSliceStart()`, diagnostic report references

**`post_upgrade_slice_settled` event**
- Recorded in `markSliceSucceeded()` via `recordEvent(...)`
- No consumer reads or acts on this event name
- Remove: the `recordEvent` call and its surrounding guard

### Files changed
- `app/src/main/java/com/u1/slicer/DiagnosticsStore.kt` — remove ~13 lines across the above
- `app/src/test/java/com/u1/slicer/DiagnosticsStoreTest.kt` — remove any assertions on the removed fields/events

### Not changed
- `clipperRetryAttempted` in `SlicerViewModel.kt` — active Clipper error recovery guard, leave alone
- `clipper_recovery_restart` — already absent from codebase

## F46 — Layer-tool Prepare 3D preview colours (Z-band recolour)

### Problem
Hueforge/layer-tool models load into the Prepare screen with the 3D mesh rendered in a single colour (the base extruder colour). The colour chips correctly show the palette, but the mesh gives no visual indication of where each colour segment appears on the model.

### Design

#### Step 1 — Expose Z→extruder segments in `ThreeMfInfo`

Add a field to `ThreeMfInfo`:
```kotlin
val layerToolSegments: List<LayerToolSegment>? = null
```
where:
```kotlin
data class LayerToolSegment(val topZ: Float, val extruderBambu: Int)  // extruderBambu is 1-based
```

Extract the `custom_gcode_per_layer.xml` parsing from `LayerToolPauseInjector` into a shared function on `LayerToolCustomGcodeXml` (or a new `LayerToolSegmentParser`). `ThreeMfParser` calls this during parse when `hasLayerToolChanges=true`, storing the result in `layerToolSegments`. `LayerToolPauseInjector` delegates to the same function instead of duplicating the parse.

#### Step 2 — Z-band recolour pass in `NativePreviewMesh` / `MeshData`

After the native Prepare mesh loads and `layerToolOnly=true`, perform a one-time recolour:

```
for each triangle in mesh:
    zCentroid = average of vertex[0].z, vertex[1].z, vertex[2].z
    extruder = layerToolSegments.lastOrNull { it.topZ <= zCentroid }?.extruderBambu ?? 1
    compactIndex = colorMapping.indexOf(extruder - 1)  // 1-based → 0-based → compact
    assign colorPalette[compactIndex] to triangle vertices
```

The 10-float vertex format already stores z at offset 2 per vertex. No new vertex data or JNI changes needed.

This logic lives in a new extension function `MeshData.recolorByZBands(segments, colorMapping, palette)`, parallel to the existing `recolor(palette)` which uses pre-assigned `extruderIndices`.

#### Step 3 — Wire into `SlicerViewModel`

In the layer-tool branch of model load (after `applyMultiColorAssignments`), when `layerToolSegments` is non-null:

```kotlin
_nativePreviewMesh.value?.recolorByZBands(
    segments = mfInfo.layerToolSegments,
    colorMapping = initialMapping,
    palette = activeExtruderColors
)
```

Uses the existing `pendingRecolor` path in `ModelRenderer` — no GL thread changes needed.

### Files changed
- `app/src/main/java/com/u1/slicer/bambu/ThreeMfInfo.kt` — add `layerToolSegments` field + `LayerToolSegment` data class
- `app/src/main/java/com/u1/slicer/bambu/LayerToolCustomGcodeXml.kt` — extract segment parsing into shared function
- `app/src/main/java/com/u1/slicer/bambu/ThreeMfParser.kt` — call segment parser when `hasLayerToolChanges=true`
- `app/src/main/java/com/u1/slicer/gcode/LayerToolPauseInjector.kt` — delegate to shared parser
- `app/src/main/java/com/u1/slicer/viewer/MeshData.kt` — add `recolorByZBands()`
- `app/src/main/java/com/u1/slicer/SlicerViewModel.kt` — call `recolorByZBands` in layer-tool load branch

### Testing
- Unit test for `recolorByZBands`: given known Z centroid values and a segment list, assert correct colour assignment
- Unit test for the shared segment parser: given sample XML, assert correct `LayerToolSegment` list
- Existing `NativePreparePreviewTest` / `ProfileEmbedderIntegrationTest` must still pass

### Edge cases
- Model has no layer-tool segments (empty XML): mesh stays single-colour (same as today)
- Triangle Z centroid below first segment: use extruder 1 (base colour)
- `colorMapping` doesn't contain the extruder index: fall back to index 0
