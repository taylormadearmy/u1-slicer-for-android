## B60: Painted supports not generated for citystep

### Root Cause

`hasPaintSupports` is silently dropped through two merge functions:

1. **`mergeThreeMfInfo()`** (`SlicerViewModel.kt:2912`) — starts with `processedInfo.copy(...)` but does not include `hasPaintSupports` in the override list. `processedInfo` was parsed with `skipPaintDetection=true`, so its `hasPaintSupports=false`.

2. **`mergeThreeMfInfoForPlate()`** (`SlicerViewModel.kt:3074`) — starts with `plateInfo.copy(...)` where `plateInfo` comes from `parseForPlateSelection()`, which also hard-codes `hasPaintSupports=false` (line 465) because it's a lightweight parse.

After plate selection for citystep, `_threeMfInfo.value` has both `isMultiPlate=false` (extracted single-plate file) and `hasPaintSupports=false` (dropped). So `needsPreserve=false` in `ProfileEmbedder.buildConfig()`, which triggers the standard Snapmaker process profile stack. That stack has `enable_support=0` in `standard_0.20mm.json`, overwriting the file's `enable_support=1`. Supports are silently disabled.

The entire rest of the pipeline is correct: `paint_supports="4"` is detected, preserved through `copyZipEntry`, and correctly decoded by the native engine as `ENFORCER`. The only bug is the two missing fields in the merge functions.

### Fix

Two one-liners in `SlicerViewModel.kt`:

- In `mergeThreeMfInfo()`: add `hasPaintSupports = origInfo.hasPaintSupports`
- In `mergeThreeMfInfoForPlate()`: add `hasPaintSupports = sourceInfo.hasPaintSupports`

### Test

Add to `MergeThreeMfInfoTest.kt`:
- `mergeThreeMfInfo preserves hasPaintSupports from origInfo` — confirm `hasPaintSupports=true` when origInfo has it, even if processedInfo has `false`
- `mergeThreeMfInfoForPlate preserves hasPaintSupports from sourceInfo` — same for the plate-selection path

## B59b: Prime tower Prepare preview doesn't refresh on toggle

### Root Cause

Two independent bugs:

1. **`togglePrimeTower()`** (`SlicerViewModel.kt:~1436`) updates `_config.value` and saves overrides but does not call `invalidatePrepareMeshCache()`. The native mesh cache remains valid with the old prime tower visibility, so the Prepare preview is stale until the user switches tabs.

2. **`InlineModelPreview` `LaunchedEffect`** (`MainActivity.kt:~2246`) has keys `(viewerView, placementEnabled, objPositions, towerX, towerY)`. `wipeTowerEnabled` / tower visibility is not a key. In the placement-enabled branch, the tower rect is set when visible but there is no `else -> v.renderer.wipeTower = null` branch when the tower is hidden. Toggling the prime tower does not re-run the effect, so the rectangle persists.

### Fix

**`SlicerViewModel.kt`**:
- In `togglePrimeTower()`: call `invalidatePrepareMeshCache()` after updating `_config.value`.

**`MainActivity.kt`**:
- Add `placementConfig.wipeTowerVisible` (or `wipeTowerEnabled`) to the `LaunchedEffect` key list.
- In the placement-enabled branch, add `else -> v.renderer.wipeTower = null` for when the tower is not visible.

### Test

Add to `PreparePreviewCacheTest.kt`:
- `togglePrimeTower clears cached prepare mesh` — simulate a loaded model with a cached prepare mesh, call `togglePrimeTower()`, verify `cachedPrepareMesh` is null. (This is a ViewModel-level unit test using a fake native library.)

## F68: Single-color mode missing material label on Preview swatches

### Root Cause

In `SliceCompleteSummaryCard` (`MainActivity.kt`), the per-extruder swatch section is guarded by:

```kotlin
if (perExtruderFilamentMm.size > 1) { ... }
```

Single-color slices have `perExtruderFilamentMm.size == 1`, so the entire block is skipped. No swatch and no material type label are shown.

### Fix

- Change the condition to `perExtruderFilamentMm.isNotEmpty()`.
- Ensure the single-slot case is handled by the existing per-extruder swatch rendering, which already calls `resolveExtruderMaterialType` and uses `buildPerExtruderDisplaySlots`.

The only change that needs care: the existing layout may assume `size > 1` for formatting reasons (e.g., "E1 / E2 / ..." labels). Verify the single-slot case renders cleanly with just the one swatch row.

### Test

Add to `PreviewSummaryMappingTest.kt`:
- `single color slice shows material type label` — build a single-extruder summary, confirm the material type is non-empty and the swatch slot is returned.

## F67: Stale slice indicator

### Problem

After the user changes any setting (layer height, supports, filament, etc.), the slice result shown on the Preview tab is stale but there is no indication of this. The bed temperature label was the reported symptom, but the underlying issue applies to all settings.

### Design

Add a `_sliceStale: MutableStateFlow<Boolean>` to `SlicerViewModel`.

**When it turns `true`**: any user-initiated config mutation — `setLayerHeight`, `setSupportEnabled`, `setFilamentProfile`, `togglePrimeTower`, `setModelScale`, `setModelRotation`, `setPlateType`, etc. Also triggers when a new model is loaded (clearing the previous result). It does NOT trigger from internal operations like embed or sanitize.

**When it turns `false`**: at the start of `startSlicing()` (or when the slice result is cleared). This resets the stale flag as soon as a new slice starts.

**UI**: A small dismissable banner shown above the Slice button (or integrated into the Slice button row) when `sliceStale && lastSliceResult != null`. Text: "Settings changed — slice again". Optionally includes an inline Slice button. The banner disappears automatically when a slice starts.

**Scope**: applies to the Slice tab only (not Prepare or Print tabs).

### Implementation notes

- `_sliceStale` is a `MutableStateFlow<Boolean>(false)` in the ViewModel.
- Exposed as `val sliceStale: StateFlow<Boolean>` for the UI.
- The UI observes `sliceStale` via `collectAsState()`.
- All config-setting functions gain a one-liner: `_sliceStale.value = true`.
- `startSlicing()` sets `_sliceStale.value = false` at the top (before the coroutine suspends into the slice pipeline).
- `clearModel()` also sets `_sliceStale.value = false` since there's nothing to re-slice.

### Test

Add to unit tests (new `SliceStalenessTest.kt` or inline in `SlicingOverridesTest.kt`):
- `sliceStale is false initially`
- `sliceStale becomes true when config changes`
- `sliceStale resets to false on startSlicing`
