# F94 + F92 — Send-prep banner + Auto-arrange

**Date:** 2026-06-03
**Features:** F94 (GitHub #166), F92 (GitHub #162)
**Status:** Design approved, pending spec review

Two independent, user-requested features. Neither needs a native `.so` rebuild. Both
follow existing patterns. Bundled into one spec/plan because they are small and will
ship together (per the release-bundling preference).

## F94 — Immediate "Preparing G-code" banner during send

### Problem

When the user taps a send action (Upload Only, Map & Print, or the Absent/legacy
path), `MainActivity` does:

1. `navigateTab(Routes.PRINTER)` — switch to the Printer tab.
2. `sendActionScope.launch(IO) { LongOpService.start("Preparing G-code"); applyPrintTimeRemap(...) ; ... }`
3. Only **after** the remap completes does it call
   `printerViewModel.sendUploadOnly(...)` / `sendAndPrint(...)`, which is the **only**
   thing that sets `SendingState.Uploading`.

On a large G-code the remap (`applyPrintTimeRemap`) can take ~80s. During that window
`SendingState` is still `Idle`, so `PrinterScreen` shows **nothing**. The user lands on
a blank Printer tab with no feedback until "Uploading G-code…" finally appears. The
foreground-service notification says "Preparing G-code", but that lives in the system
shade, not on the screen the user is looking at.

Reporter (Discord, 2026-05-30): *"Any chance it could post something at the top of the
printer screen while it's preparing the file. It eventually showed up as uploading
gcode but I didn't get that immediate satisfaction to know it was working."*

### Design

**1. New sending state.** Add to `PrinterViewModel.SendingState`:

```kotlin
/** File is being prepared (remap/copy) before the upload begins. */
object Preparing : SendingState()
```

**2. Synchronous trigger.** Add to `PrinterViewModel`:

```kotlin
/** Show the "Preparing G-code" banner immediately on send-action tap,
 *  before any IO begins. Flipped to Uploading by sendUploadOnly/sendAndPrint. */
fun beginSendPreparing() { _sendingState.value = SendingState.Preparing }
```

Call `printerViewModel.beginSendPreparing()` on the Main thread at all **three**
send-confirm sites in `MainActivity`, right next to the existing
`navigateTab(Routes.PRINTER)`:
- `PendingMappingSend.Action.UploadOnly` → `onConfirm` (~line 838).
- `PendingMappingSend.Action.PrintAndUpload` → `onConfirm` (~line 918).
- The `CanonicalLookup.Absent` path (~line 967).

Because `onConfirm` runs on the Main thread, the state flips before the IO launch — the
banner appears the instant the user confirms.

**3. Render the banner.** In `PrinterScreen` (the `when (sendingState)` block at
[PrinterScreen.kt:225](../../../app/src/main/java/com/u1/slicer/ui/PrinterScreen.kt)),
add a `Preparing` arm above the `Uploading` arm, reusing the existing `Uploading` card
layout (surfaceVariant container, `CircularProgressIndicator` + two-line text):

- Title: `"Preparing G-code…"`
- Subtitle: `"Getting your file ready to send"`

The existing `Uploading` card then takes over when `sendUploadOnly`/`sendAndPrint` flips
the state, followed by `UploadComplete` / `PrintStarted`. No change to those arms.

**4. Stuck-state guard (latent bug fix).** Today, if `applyPrintTimeRemap` throws, the
send coroutine propagates the exception, `sendUploadOnly` is never reached, and
`SendingState` stays `Idle` (silent failure — pre-F94 this was invisible). With F94 it
would stay `Preparing` forever. Wrap the prep step in each of the three send coroutines
so a failure sets `SendingState.Error`:

```kotlin
sendActionScope.launch(Dispatchers.IO) {
    LongOpService.start(toastContext, "Preparing G-code")
    val physical = try {
        applyPrintTimeRemap(...)            // or prepareExportableGcodeWithMapping(...)
    } catch (t: Throwable) {
        withContext(Dispatchers.Main) {
            printerViewModel.reportSendError("Couldn't prepare G-code: ${t.message}")
        }
        return@launch
    } finally {
        LongOpService.stop(toastContext)
    }
    ...
}
```

Add `PrinterViewModel.reportSendError(msg: String)` setting `SendingState.Error(msg)`.

### Scope

- **Send actions only** — not slicing (the report is specifically about the send→upload
  gap on the Printer screen).
- No native work. No new files (edits to `PrinterViewModel`, `PrinterScreen`,
  `MainActivity`).

### Tests

- `PrinterViewModelTest` (JVM): `beginSendPreparing()` sets `Preparing`;
  `reportSendError()` sets `Error`; a `Preparing → Uploading → UploadComplete`
  transition sequence holds (drive the existing send methods with a fake repo).
- Structural/behavioural: existing instrumented Printer tests remain green. (No Compose
  UI harness in the project; the on-screen banner appearance is covered by manual E2E.)

## F92 — Auto-arrange (translation-only, tower pinned)

### Problem

There is an "Auto-orient all" action but no "Auto arrange". Users must hand-place each
object/copy on a small phone screen, which is error-prone. One user printed a large
object that visually merged with the wipe/purge tower because they didn't notice the
overlap. The split-to-parts and per-part-copies flows (F93) make manual arrangement
harder still.

Reporter (Discord, 2026-05-31): *"I see there is an auto orient, is there an auto
arrange I am missing? I printed a large object that merged with my print tower because I
didn't pay attention."*

### Decisions (from brainstorming)

- **Translation-only** — keep each object's current rotation/scale; just move objects.
  No rotation nesting (that would need a real solver / native work).
- **All objects on the bed** — arrange every distinct object/instance; a lone object is
  re-centered clear of the tower.
- **Entry point** — "Auto-arrange all" in the overlay `MoreVert` menu beside
  "Auto-orient all".
- **Tower stays pinned** — the wipe tower keeps its current position
  (`SliceConfig.wipeTowerX/Y`, default back-of-plate per F75). Objects pack **around**
  the tower's fixed footprint, treated as a reserved rectangle. (Simpler than moving the
  tower: no read-back step, and it preserves the position users expect.)

### Design

**1. Pure layout function** in `CopyArrangeCalculator`:

```kotlin
data class ArrangeResult(
    val positions: FloatArray,      // flat [x0,y0,x1,y1,...] min-corner, mm
    val overflowCount: Int,         // objects that couldn't be placed on-bed
)

/**
 * Packs N object footprints into the bed using a shelf/row packer, skipping any
 * placement that would overlap [reservedRect] (the pinned wipe tower, when enabled)
 * or fall outside the bed. Objects that don't fit are left at their incoming position
 * and counted in overflowCount — never placed off-bed (the structural fix B135 needs).
 *
 * @param boxes flat [sX0,sY0,sZ0, ...] from getObjectBoundingBoxes() (already
 *   post-rotation, so translation-only keeps rotations).
 * @param reservedRect [minX,minY,maxX,maxY] of the pinned wipe tower + margin, or null.
 * @param incoming current positions, used as the fallback for overflow objects.
 */
fun autoArrange(
    boxes: FloatArray,
    reservedRect: FloatArray?,
    incoming: FloatArray,
    bedSize: Float = 270f,
    margin: Float = 5f,
): ArrangeResult
```

Algorithm (shelf packer, bottom-to-top, left-to-right):
- Sort placement order largest-area-first for better packing (stable; ties keep input
  order so results are deterministic for tests).
- Maintain a cursor `(curX, curY)` and `rowMaxY`. For each object, find the first
  on-bed position at/after the cursor whose AABB does **not** overlap `reservedRect`;
  if the current row can't fit it (would exceed `bedSize - margin` in X) wrap to the
  next shelf (`curY += rowMaxY + margin`).
- If no on-bed, non-overlapping position exists, leave the object at its `incoming`
  position and increment `overflowCount` (graceful — caller warns; nothing off-bed).
- Center the produced grid on the bed where space allows.

**2. ViewModel orchestration** — `SlicerViewModel.autoArrangeAll()` (suspend) +
`launchAutoArrangeAll()` (fire-and-forget wrapper, mirroring `launchAutoOrientAll`):

```kotlin
fun launchAutoArrangeAll() { viewModelScope.launch { autoArrangeAll() } }

suspend fun autoArrangeAll() {
    val ctx = beginLongOp("Auto-arranging")
    try {
        val boxes = native.getObjectBoundingBoxes() ?: return
        val n = boxes.size / 3
        if (n == 0) return

        // Reserved rect = pinned wipe tower footprint (+ margin) when prime tower on.
        // Tower-enabled is read via the same path buildProfileOverrides uses
        // (slicingOverrides.primeTower.resolvePrimeTower(slotCount, cfg.wipeTowerEnabled)).
        val cfg = _config.value
        val ov = slicingOverrides.value
        val reserved = if (/* prime tower enabled */) {
            val w = resolveWipeTowerWidth(cfg, ov)
            val d = resolveWipeTowerDepth(lastModelInfo?.sizeZ ?: 0f, ov)
            floatArrayOf(cfg.wipeTowerX - 5f, cfg.wipeTowerY - 5f,
                         cfg.wipeTowerX + w + 5f, cfg.wipeTowerY + d + 5f)
        } else null

        // Incoming positions for overflow fallback: current custom positions, else the
        // live world-AABB mins (xy pairs from nativeGetObjectWorldAABBMins), else zeros.
        val incoming = currentObjectPositionsXY(n)
        val result = CopyArrangeCalculator.autoArrange(boxes, reserved, incoming)

        if (n > 1) {
            // Multi-object path — same as split / multi-file / duplicate.
            withContext(Dispatchers.IO) { native.setObjectPositions(result.positions) }
            hasMultipleDistinctObjectsVar = true
            customObjectPositions = result.positions
            _multiObjectPositions.value = result.positions
        } else {
            // Single object: re-center via the instances path. Do NOT call
            // setObjectPositions or flip hasMultipleDistinctObjectsVar — that would
            // push a single-file model into multi-object renderer mode (the B124 hazard).
            withContext(Dispatchers.IO) {
                native.setModelInstances(result.positions)   // 1 xy pair
            }
        }
        _sliceStale.value = true
        invalidatePrepareMeshCache()
        if (result.overflowCount > 0)
            _toastEvents.tryEmit("${result.overflowCount} object(s) didn't fit on the bed")
    } finally { endLongOp(ctx) }
}
```

Notes / edge cases:
- **Single object (n == 1):** the packer with one box re-centers it clear of the
  reserved rect. Applied via the **single-object instances path** (above) so it never
  flips into multi-object renderer mode.
- **Tower not moved:** we never write `wipeTowerX/Y` — the tower stays pinned.
- Boxes are post-rotation, so rotations are preserved (translation-only).
- `currentObjectPositionsXY(n)` and the exact instances-apply call are to be confirmed
  against the live single-object placement code during planning; the design contract is
  "re-center via the existing single-object mechanism, multi-object via setObjectPositions".

### Relationship to B135

B135 (CopyArrangeCalculator places pieces off-bed when the row+below grid is exhausted)
is explicitly the case Auto-arrange exists to fix. `autoArrange` is on-bed-guaranteed
(overflow is reported, never placed past the edge). After this lands, the B135
4-duplicate replay test variant (`B131B132B133DiagnosticTest`, currently relaxed to 2
dupes) can be un-ignored if a follow-up wires duplicate placement through `autoArrange`
— tracked as a B135 follow-up, not in scope here.

### Tests

- `CopyArrangeCalculatorTest` (JVM): `autoArrange` —
  1. two objects, no tower → side-by-side, both on-bed, no overlap.
  2. objects + reserved tower rect → no object overlaps the rect; all on-bed.
  3. more objects than fit → `overflowCount > 0`, no position off-bed, overflow objects
     left at `incoming`.
  4. single object → centered, clear of the reserved rect.
  5. row-wrap: objects wider than one row wrap to the next shelf without overlap.
- Instrumented (`SlicingIntegrationTest` or `PreparePreviewViewModelTest`): load a
  multi-object layout, call `autoArrangeAll()`, assert pairwise object AABBs don't
  overlap, none overlap the wipe-tower footprint, and all are within `0..270`.

### Scope / non-goals

- No rotation nesting, no native rebuild, no tower repositioning.
- Duplicate-placement rewrite through `autoArrange` (the full B135 fix) is a follow-up.
