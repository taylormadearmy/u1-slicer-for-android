## B89 — Info menu scrollable

### Symptom
`ModelInfoDialog()` in `MainActivity.kt:2783` renders metadata + action buttons in a non-scrolling `Column`. Long filenames or portrait orientation push the "Close" button below the viewport and out of reach.

### Red test
`app/src/test/java/com/u1/slicer/ui/ModelInfoDialogTest.kt` (new file).

Use `createComposeRule()`. Render `ModelInfoDialog` with:
- a 120-char filename
- full metadata (format, dimensions, triangles, plate, extruders, etc.)
- container height 520dp (small portrait)

Assert: the node with text "Close" has an ancestor with a scroll action (`hasScrollAction()`), and is reachable via `performScrollTo()` without throwing.

The red test fails today because the Column has no `verticalScroll` modifier.

### Fix
In `MainActivity.kt:2806`, wrap the Column body in `.verticalScroll(rememberScrollState())`. Keep the title Row + filename ellipsis pinned above the scroll region (so the filename + title never scroll away — only the metadata rows + buttons do).

Inline diff sketch:

```kotlin
val scrollState = rememberScrollState()
Column(
    modifier = Modifier.verticalScroll(scrollState),
    verticalArrangement = Arrangement.spacedBy(6.dp),
) { /* metadata + action buttons */ }
```

### Green
Same test passes; render looks identical for short filenames, scrolls for long ones.

### Risk
None material. Compose `verticalScroll` on a Column inside AlertDialog is idiomatic.

## B88 — Plate-switch colour mapping leak

### Symptom
On multi-plate Bambu 3MFs, switching plates without reloading the file retains the previous plate's `_colorMapping`. When the new plate has a different colour palette, Prepare preview paints the new mesh using the previous plate's extruder assignments — producing wrong colours, sometimes a single colour where two were expected. On at least one plate (Buzz Lightyear plate 9) the slicer output also diverges from Prepare preview.

### Root cause hypothesis
`SlicerViewModel.selectPlate()` at `SlicerViewModel.kt:1030`:
- Resets `toolRemapSlots` and `semmColorPermutation` (correct).
- Re-runs `mergeThreeMfInfoForPlate()` so `detectedColors` are fresh (correct).
- Does **not** re-derive `_colorMapping` against the new `detectedColors` + current extruder presets. The prior plate's mapping persists.

B86's fix established that `colorMapping` must be derived via `findClosestExtruder` against stored user presets (`settingsRepo.extruderPresets.first()`). `selectPlate()` omitted this step.

### Red test
Instrumented — add to `PreparePreviewViewModelTest.kt`:

```kotlin
@Test
fun buzzLightyear_plateSwitch_reDeriveColorMappingPerPlate()
```

1. Copy `Buzz_Multipart_3MF_Bambu.3mf` to cache, call `loadModelFromFile`.
2. Assert multi-plate detected.
3. Select plate with 2 distinct detected colours (e.g. plate 1 — confirm during inspection).
4. Capture `colorMapping_plateA` and distinct-colour-count-in-preview-mesh.
5. Call the plate-switch path (same one the "Change plate" chip uses) to a plate whose detected colours differ from plate A (e.g. plate 9).
6. Assert:
   - `colorMapping_plateB` was re-derived: `colorMapping_plateB == findClosestExtruder(detectedColors_plateB, presets)`.
   - distinct-colour count in plate B's preview mesh matches plate B's detected-colour count (not plate A's).
7. Switch back to plate A, re-assert plate A's mapping is correctly re-derived too (no stickiness).

Fails today because `_colorMapping` is stale after switch.

### Fix
In `SlicerViewModel.selectPlate()` after `mergeThreeMfInfoForPlate()`:

```kotlin
val presets = settingsRepo.extruderPresets.first()
val freshMapping = findClosestExtruder(newDetectedColors, presets)
_colorMapping.value = freshMapping
refreshMappedPreviewColors()   // keep activeExtruderColors in lockstep
```

Must suspend on `.first()` (B86 contract) so the real DataStore presets are used, not the initial placeholder. If `selectPlate()` is not already a `suspend fun` running on a coroutine, wrap the new logic in a launched scope and emit the mapping through the existing StateFlow.

### Green
- New red test passes.
- Existing regression guards stay green:
  - B83 plate-switch objectIds stable-source test.
  - B86 S-Buttons preset race test.
  - All existing `PreparePreviewViewModelTest` tests for Dragon, Shashibo, H2C benchy.

### Decision — manual colour overrides
When the user manually changed extruder assignments while on plate A and then switches to plate B, we **re-derive fully** on plate B. Rationale: each plate is an independent scene with its own palette; carrying manual overrides makes no sense when the target palette differs. This matches behaviour on fresh load.

### Risk
Low. Isolated to `selectPlate()`. Unit tests for `findClosestExtruder` and `refreshMappedPreviewColors` already exist.

## B87 — Black bottom layers dropped from slice

### Symptom
User DC15: Skywing Seawing Hybrid Dragon 3MF shows black on bottom layers in Prepare preview, but:
- G-code preview after slicing has no black on those layers.
- The actual printed part also has no black on those layers.

Critical: this is **not** a preview-rendering bug. The slicer's G-code output is wrong. Prepare preview reads native mesh with `paint_color` triangles correctly; the slice pipeline drops the bottom-layer colour switch.

### Investigation plan
Before writing a fix, inspect `天翼，海翼，丝翼拆件多色.3mf` to determine the colour-bearing mechanism:

1. Unzip the 3MF.
2. Inspect `Metadata/model_settings.config` — is this a per-object extruder model, a SEMM (`paint_color`) model, or a layer-tool model (`custom_gcode_per_layer.xml` type=1/2)?
3. Count `paint_color` / `mmu_segmentation` triangles, note Z distribution.
4. If `custom_gcode_per_layer.xml` exists, check layer indices of type=1/2 entries — are there entries for layers 0, 1, 2?
5. Check `project_settings.config` for `filament_colour` ordering and `bottom_shell_layers`.

Three candidate root causes, each with a different fix:

#### Candidate A — Layer-tool XML layer-0 off-by-one
If the 3MF encodes colour changes via `custom_gcode_per_layer.xml` with type=1 (colour change) at layer 0 or 1, and `LayerToolCustomGcodeXml.parseLayerToolCustomGcodeXmlPerPlate` or `LayerToolPauseInjector` skips layer 0 (treating "first layer's tool" as implicit), the first colour would never emit a `T<n>`.

Fix: make injector explicit at layer 0 — emit the initial tool selection as an explicit `T<n>` before layer 0 even if it equals default T0.

#### Candidate B — Paint segmentation drops bottom triangles
If this is a SEMM model (`paint_color="X"` per triangle) and the black region covers the first 2–3 layers only, OrcaSlicer's paint segmentation may be filtering out segments below a Z threshold or discarding layers where the painted region is a full layer (treating as base).

Fix: native — adjust paint-segmentation threshold or override per-region first-layer handling. Requires `.so` rebuild with NDK 26 Release, per CLAUDE.md.

#### Candidate C — Per-object extruder not applied to bottom shell
If the 3MF encodes bottom-layer colour via a *separate object* with its own `extruder` attribute that happens to sit below Z=0 or overlapping the main object's first layers, and `BambuSanitizer` or `mergeThreeMfInfoForPlate` drops non-primary objects or merges them incorrectly, the bottom colour vanishes.

Fix: in the Bambu pipeline — preserve per-object extruders for overlapping sub-objects.

### Decision log

**2026-04-22 — Root cause identified: shared with B88**

1. Inspected `天翼，海翼，丝翼拆件多色.3mf`: SEMM model with 3 declared filaments
   (cyan/purple/white) and paint_color attributes using states 0, 4, 8 (first-char
   hex values). No custom_gcode_per_layer.xml; no per-object extruder overrides
   (all `extruder="1"`).

2. Native `applyItsPreviewMesh` emits `state_idx - 1` as the extruder index for
   painted triangles. Paint states 4 and 8 → raw mesh indices 3 and 7. Because
   `has_mmu_data=true`, native `compactPreviewIndices` is SKIPPED.

3. `MeshData.recolor` sees palette size = 3 (one per declared filament), clamps
   raw index 3 → 2, raw index 7 → 2. The two painted surface classes collapse
   onto a single palette entry — "bottom layers look like one colour" in Prepare.

4. The slicer `slice()` output is correct — `SemmSlicingTest.skywingSeawingDragon_
   sliceProducesMultipleToolChanges` confirms T0=12, T1=8, T2=10 with all three
   tool indices present in the first 3 printed layers. So the G-code preview
   (which uses `normalizeGcodePreviewColors` on compact T-indices) shows three
   distinct colours, while Prepare (pre-fix) shows at most two.

5. **The B88 compaction fix in `NativePreviewMesh.toMeshData()` also resolves
   B87**: compacting raw indices 0, 3, 7 → 0, 1, 2 aligns Prepare's palette
   lookup with the G-code preview's compact-T-index lookup. No separate B87
   code change is required.

**Verification**: `SemmSlicingTest.skywingSeawingDragon_sliceProducesMultipleToolChanges`
confirms slice integrity. `NativePreviewMeshCompactionTest` (B88) covers the
compaction guarantee at the unit level. A `PreparePreviewViewModelTest` for
Skywing plate 1 was drafted but hit an unrelated timeout during on-device
`selectPlate(1)` load (native `loadModel` never completed within 3 minutes
after `restructurePlateFile: no multi-color components, skipping`). That
slow-load behaviour is separate from the colour-mapping bug and is logged
as a follow-up (see below) rather than blocking B87's close-out.

**Follow-up (non-blocking)**: On-device `selectPlate(1)` for Skywing hangs
after plate extraction. Could be legitimate slowness (700k triangles,
painted, re-embed) or a real bug. If user reports continue, investigate
separately — B87's user-visible symptom is resolved by the B88 fix.
